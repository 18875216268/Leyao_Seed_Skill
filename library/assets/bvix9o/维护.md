

# 能力库维护（蒸馏规范 · 自动到提案）

> 定位：本资产（能力库）三件套的**保鲜机制**——与知识库卡机制**同构**：自动提炼 → 守门 → 提案落地。
> 自动时点：与卡刷新**同一个每日 14:00 任务**（不新增调度器）。**红线**：资产内容只读——本规范产物**只到提案**，落地须批准 ✗。

## 一、三个产物与素材（均取自用户区）

| 产物 | 素材 | 更新方式 |
| --- | --- | --- |
| **经验** → `公共经验.md` | 轨迹 `traces.json` · 自动档 `memory.md`（有效做法/失效模式）· 用户纠正 `--override` · `task_set_results.jsonl` | 追加/修正条目（带证据指针） |
| **场景** → `高频场景指引/` + `README.md` 索引一行 | 重复任务（**同场景 ≥2 次**）且无对应指引 | 新增场景文件 + 索引加一行 |
| **技能** → `公共技能.md` | 技能安装/使用记录 · 市场新能力 | 新增条目 / **反向下线**失效条目 |

## 二、四重门槛（借鉴 ECC 规则蒸馏·防噪声）

① **≥2 次复现**（跨任务/跨批次合计有效）② **可执行**（写成"做 X / 不做 Y"）③ **有明确坑或风险**（一句话说清后果）④ **未被现有条目覆盖**（含换句话说的等价内容）。
→ 任一不满足即**不入账** ✗（留在日志等样本来）。

## 三、流程（每次 ≤3 条提案）

1. 读素材（上表）→ 2. 按门槛筛选 → 3. 与现有条目**去重** → 4. 生成提案（`python evolution/grow.py propose --kind asset_write --payload '<JSON>'`，附**证据指针**：任务 / 时间 / 命中 id）→ 5. 批准后落地。
去重记录与结果写入用户区（避免下轮重复提议）；**每次 ≤3 条**，防提案洪水。

## 四、边界（与相邻层分工）

- 场景文件**一次成稿、只读不改**（修订 = 新文件 + 索引改一行）；
- 不写业务数据、不写凭证、不写未验证结论（"待验证"须显式标注）；
- 与进化层分工：进化层管**自动档经验**（`memory.md`）；本规范管**把经验 / 场景 / 技能升格进资产**（走提案）✗ 不越权。


## 五、减法与重校准（照 MetaRSI「Harness 可做减法 + 自述会过期」）

- **减法（能力内化后删冗余）**：某条经验/场景**被内化**进更便宜的载体后（写入判据、常驻规则、或卡条目已能覆盖），
  原条目即变冗余 → **走提案退休**（移入"已退休"区并留墓碑：指纹 + 退休理由 + 被谁取代），**不静默删除** ✗。
  判据：**回放校验**——把该条目移除后，重跑相关任务/演练仍全过 → 可退休；否则保留。
- **自述过期重校准（定律二）**：能力一变，旧自述即失真 → 每次蒸馏顺带核对三类自述是否仍准确：
  ① 本资产三件套的标题/摘要；② 路由节点【何时用】与【别名】；③ 框架自述（`SKILL.md` / 层级总览）。
  失真 → 生成提案修正（含证据：哪次任务暴露的）。
- **边界标定（Data-RSI 口径）**：经验条目除"做法"外，尽量标注**能力边界**（在什么条件下有效 / 在什么条件下失效），
  供上游（卡/判据）沿用——边界写不出者视为"待验证"，不升格 ✗。


> **权限门槛**：本规范第 4 步的 `asset_write` 提案**仅维护者实例**可用；**非维护者实例 propose 即被拒收**——改用管理台（`library/admin/console.py`）显式维护，或产出同格式条目交由维护者收编（不硬凑 ✗）。


## 六、索引预算核对（增长侧前置 · 可执行）

> 依据 `SKILL.md` 标准调用链：能力库索引**硬上限 = 每个索引文件 ≤20 条目 / ≤2 KB**。索引只增不减会吃掉默认层的成本优势 ✗。

**每次"索引加一行"之前，先核对**（两条都过才可加；不过 → 先做减法再谈加法 ✗）：
1. **数条目**：打开该索引文件，数 `-`/`|` 开头的条目行 —— `≥20` → 触顶，**禁止再加**；
2. **量字节**：看该文件大小 —— `≥2 KB（2048 字节）` → 触顶，**禁止再加**。

**触顶后的动作（按序）**：
① 先按 §五「减法」退休已内化/低频条目（回放校验通过才退）→ 腾位后再加；
② 仍不够 → 把该索引**拆分**为子目录 + 子索引（同 `ROUTES.md` 的分片口径：单文件超限即拆，父索引只留指针行）；
③ 拆分方案写入提案说明（含前后条目数/字节数），批准后落地 ✓。

**记录**：每次触顶处理（退休 n 条 / 拆分 m 个文件）与结果写入用户区台账（与 §三 同处，避免下轮重复处理）。
