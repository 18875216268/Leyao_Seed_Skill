# ⑤ 交付

按报告框架交付；口径随行；经验沉淀。

## 输入

验收步通过的产物与口径标注（含验收留证）。

## 出口判据（全过才算任务完成）

- [ ] 交付物**只在 `03-结果交付区/`**、命名合规（ASCII 小写、无 `final/v2`）；旧版已入 `04-归档区/`；工作区根目录除四区（+可选 `README.md`）外**无散落文件**
- [ ] 报告框架五要素齐备，口径随行
- [ ] 轨迹已追加（`grow.py trace`，一次任务一条）
- [ ] 任务集台账已登记（`run_task_set.py --record`，一次任务一条；**台账只写用户区**）

## 动作

1. **按框架组织**：结论先行 → 关键发现（按重要性）→ 支撑细节（表格优先）→ 口径与假设（时间范围/主体/排除项）→ 后续建议（只给有依据的）。骨架见 `processor/shapes.md`。
2. **交付物落位（硬）**：沿用 ② 规划已确定并明示的 `<work-dir>`（中途变更须在交付说明开头明示新目录）。
   - `03-结果交付区/` **只放最终确认版本**；旧版移入 `04-归档区/`（**不静默删除**，条目 = 时间戳 + 来源 + 原因）；
   - 中间产物在 `02-任务执行区/临时产物区/`、用户原始材料在 `01-原始材料区/`；
   - **根目录判据**：工作区根下只允许四区（+ 可选 `README.md`），发现散落文件 → 按归属三问归位（移动前出清单、记原路径，可还原）；
   - 交付件命名：`<用途>-<YYYYMMDD>.<ext>`（ASCII、小写、无空格；**不写** `final/v2/最终`，也不写版本后缀——"当前版"就是它，历史在归档区）。
3. **口径随行**：每个关键数字带口径（时间范围/含税与否/主体范围）——不带口径的数字无法被复核、等于不可用，故**不出口**；事实给来源、推断给链条（混写会让读者分不清哪句可采信）。
4. **沉淀**：追加一条轨迹进自我进化层（**一次任务只追加一条**，多轮追问不重复追加）——`python evolution/grow.py trace --task "<任务>" --routed "<命中的节点 id / 无命中写 none>" --outcome success|partial|fail [--reason "<失败原因>"] [--override "<用户纠正>"] [--no-auto]`。`--routed` **必须写节点 id**（见 `library/ROUTES.md` 各节点行首），它是规则归属与命中率统计的唯一依据；`trace` 时会**自动**再跑 `grow.py reflect` / `grow.py evolve`（变→择 自动闭环，经验立即进 memory 自动档；`--no-auto` 可关）；文档 / 路由 / 资产内容仍走 `grow.py propose` 提案守门。
   **用户纠正必须采集（硬）**：本次若用户**明确纠正**了路由选择或做法（如"别走 X，应该走 Y""这个口径不对""以后都按 Z 来"），**必须**把原话摘要写入 `--override`——它是本层**最强的学习信号**（`reflect` 的 route 候选主要来自它）；漏采 = 这次纠正白丢了，下次还会犯。
   **outcome 必须如实（硬）**：三档定义——`success` = 需求逐项通过 **且** 验收 rubric 达标 **且** 关键数字换法复核一致；`partial` = 已交付但有未达标项（必须在 `--reason` 写明差在哪）；`fail` = 未交付 / 验收不过（必须写 `--reason`）。
   **禁止把失败或半成品写成 success**：依据（Ratchet 正文 + 2026 环境锚定审计研究）——**false pass 是致命方向，任何样本量都救不回**，且会让进化层学到**错的规则**（污染「有效做法」，比不学更糟）；成功声明须能给出**可执行证据**（命令 / 产物路径 / 数字复核），"**没有验证就宣称完成 = 不诚实，不是效率**"（verification-before-completion 实践）。
   同一步顺带**登记任务集台账**（一次任务一条）：`python evolution/tests/run_task_set.py --record`——把本次产物的四档判定追加到用户区 `data/state/task_set_results.jsonl`（pass^k 累积台账；**只写用户区，不改包内**）。

## 红旗

- 交付物里混入中间产物（草稿/临时脚本/中间数据）。
- 工作区根目录出现散落文件或文件夹（四区之外）。
- 过程记录停在半途（关键动作没实时追加，事后补不出准确的 KI/决策）。
- 经验直接手改进共享文档（绕过自我进化层提案）。

## 引导（可裁量，非判据）

- **"关键发现 3-5 条"是引导，不是判据**：确有 6 条以上且都重要时，附一节"次要发现"，不要硬压成 5 条，也不要全塞进主节。
- **结论先行的写法**：第一句要能独立成立（把结论放最前），别用"经过分析…"开头。
- **后续建议的门槛**：只给"有依据 + 可执行"的（依据 = 本次数据 / 资产文档 / 经验记忆）；"可以考虑"类空话不写。
- **交付前最后一问**：把交付物当成"别人只读它、不问你"来读一遍——读不出结论、或读不出数字口径的，就是还没写完。
- **交付前机器核对（可选；实测证明有效）**：交付前用一次性脚本对本次产物做"机器可判定"自检——四区齐备 ｜ 命名合规（**文件 ASCII 小写 + 日期**、目录中文）｜ 契约表无"进行中" ｜ rubric 逐条有证据 ｜ 凭证/口令零泄漏。**依据（本机实测 2026-09-12）**：判据存在 ≠ 执行不漏——正是这一步抓出了"交付件误用中文文件名"的违规；判据是"应该做"，机器核对是"实际做了"。
- **归档条目格式**（进 `04-归档区/IMPORT.md`，一行一条；口径来自 ISO 15489 的"处置须系统化、可追溯"）：`<YYYY-MM-DD HH:MM> ｜ <来源路径> ｜ <归档原因：旧版本/不适用/过时> ｜ 由 <谁/哪一步> 归档`
- **交付件命名示例**：`outbound-stats-20260912.xlsx`（用途-日期，ASCII 小写）；被替换的旧版移入归档时**保留原名 + 追加归档日期**（如 `outbound-stats-20260912-x20260913.xlsx`），保证归档区内按名排序≈按时间排序。
- **交付前补一行"路由复盘"**（写进过程记录 D 区，一条即可）：本次路由的**四格归类**（命中 / 虚报 / 漏报 / 正确亲做）+（若误选）**成因**（描述缺失 / 描述含糊 / 门槛过松 / 复核未执行 / 资产不可用）——归类决定下一步修哪里：改描述、调门槛，还是加复核，**不要只统计不改进**。
